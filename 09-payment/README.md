# 09. 인앱결제와 크레딧 회계

클라이언트가 보낸 결제 결과를 그대로 믿던 구조 대신, 스토어 서버에 다시 물어 확인하고 모든 크레딧 증감을 원장 1행으로 남기며, 동시 요청과 실수를 DB 제약과 조건부 갱신으로 막는 구조로 자리 잡았다.

## 1. 스토어 검증  →  `1-store-verification/`
**어디서** 팬 플랫폼 서비스 · 2026.06
**문제** 앱이 "결제 성공" 이라고 보내는 값은 위조할 수 있다. 구글은 구독을 3일 안에 확인하지 않으면 자동 취소하고, 소모품은 소비 처리를 안 하면 다시 살 수 없다. 애플은 운영 · 샌드박스 알림을 같은 URL 로 보낸다.
**바꾼 것** 구글은 서비스 계정으로 토큰을 받아(동기 라이브러리라 스레드로 넘김) 상품 구매 · 구독을 스토어 API 로 검증하고, 소모품은 소비 · 구독은 확인 호출까지 서버가 한다. 애플은 서버 알림의 JWS 를 루트 인증서 체인 · 번들 ID · 앱 ID 로 검증하되 운영 환경으로 먼저 시도하고 실패하면 샌드박스로 다시 시도한다. 거래 · 구독 조회도 운영 → 샌드박스 순으로 폴백한다.
**결과** 위조 요청은 핸들러에 닿기 전에 거부된다. 애플 알림에서 REFUND 같은 종류는 아직 로그만 남긴다.
**코드** `google_play_service.py` — 검증 · 소비 · 구독 검증 · 확인 4종 · `apple_verify_service.py` — 운영 → 샌드박스 순 JWS 검증, 거래 · 구독 재조회

## 2. 서버 알림  →  `2-server-notifications/`
**어디서** 팬 플랫폼 서비스 · 2026.06
**문제** 갱신 · 취소는 앱이 꺼져 있어도 일어나므로 스토어가 서버로 알려 줘야 한다. 알림은 재전송될 수 있고, 같은 구매 확인 요청이 동시에 두 번 들어올 수도 있다.
**바꾼 것** 알림 본문은 "무언가 바뀌었다" 는 신호로만 쓰고 구매 토큰으로 스토어 원본을 다시 조회해 만료일 · 플랜 · 지역을 확정한다. 구매 행은 주문 ID 에 unique 제약을 두고, 먼저 조회로 빠르게 거부한 뒤 그래도 끼어든 동시 요청은 unique 위반을 잡아 409 로 바꾼다. 갱신은 같은 (유저, 상품, 만료일) 이력이 있으면 재전송으로 보고 건너뛴다. 플랜을 바꾸면 토큰이 바뀌므로 이전 토큰으로도 구독 행을 찾는다. 소비 처리는 지급 확정 뒤에 하고, 실패하면 미소비로 남겨 배치가 재시도한다. 두 스토어 모두 처리 실패에도 200 을 돌려 재시도 폭주를 막는다.
**결과** 재전송 · 동시 요청에도 지급은 한 번이다. 알림을 놓쳤을 때를 위한 주기 대사(reconcile) 는 아직 없다.
**코드** `store_webhook_router.py` — 두 스토어 알림 수신, 항상 200 · `purchase_handler_service.py` — 원본 재조회, unique 위반 → 409, 만료일 기준 갱신 dedup

## 3. 크레딧 원장  →  `3-credit-ledger/`
**어디서** 팬 플랫폼 서비스 · 2026.07
**문제** 유저 행의 잔액 숫자 하나만 갱신하면 어디서 늘고 줄었는지 알 수 없고, 상품 가격이 바뀌면 과거 결제가 얼마였는지도 사라진다. 잔액 검사와 차감이 두 문장이면 동시 요청이 사이에 끼어 음수 잔액이 난다.
**바꾼 것** 모든 증감을 원장 1행으로 남긴다 — 종류 · 금액 · 변동 후 잔액 · 참조 유형 · 참조 ID. 구매 · 갱신 행에는 지급 시점의 크레딧 수량과 유저 지역 통화 기준 금액을 스냅샷으로 저장해 상품 설정이 바뀌어도 기록이 흔들리지 않는다. 차감은 `잔액 ≥ 금액` 조건이 붙은 UPDATE 한 문장으로 하고 영향 행 수가 0 이면 부족으로 판정한다. 차감 금액이 세션 길이로 정해지는 음성 정산은 유저 행을 잠가 직렬화한다. 생성 실패 환불은 먼저 커밋하고 그 다음에 알림을 보낸다 — 알림이 실패해도 환불은 남는다.
**결과** 잔액 캐시와 원장 합산이 일치하는지 검증할 수 있게 됐고, 동시 차감에도 음수 잔액이 나지 않았다. 원장이 길어지면 시점 잔액은 `balance_after` 로 읽고 총액은 DB SUM 으로 낸다.
**코드** `credit_ledger_model.py` — 원장 · 구매 · 갱신 이력 모델, 스냅샷 컬럼 · `credit_ledger_repository.py` — 조건부 UPDATE 차감, 행 잠금, DB SUM · `refund_first_commit.py` — 환불 먼저 커밋 후 알림, 거절 환불 원장

## 4. 방어 코드  →  `4-guards/`
**어디서** 팬 플랫폼 서비스 · 2026.08
**문제** 언팔로우 API 가 구독 행을 지우는데, 유료 구독자가 누르면 스토어 결제는 계속되고 앱 혜택만 사라졌다. 별개로 참조 유형 컬럼이 20자인데 환불 3종 값이 21~23자여서 MySQL STRICT 모드에서 INSERT 가 실패했고, 호출부가 예외를 삼키는 구조라 크레딧이 환불되지 않고 알림도 건너뛴 채 조용히 지나갔다.
**바꾼 것** 언팔로우는 유료 등급이고 만료일이 지나지 않았으면 서버가 409 로 거부하고, 프론트는 스토어 해지 안내 모달로 분기한다 — 이중 방어다. 참조 유형은 세 값을 20자 이내로 축약하고, 컬럼 정의 바로 옆에 상한과 사고 경위를 적어 새 값을 짓는 사람이 반드시 보게 했다. 환불 블록은 알림 발송과 같은 try 에서 떼어 따로 감싸고, 실패하면 ERROR 로 남겨 운영 로그에서 환불 누락을 검색할 수 있게 했다.
**결과** 돈은 내는데 혜택이 없는 상태가 재현되지 않았고, 환불 실패가 다른 오류에 묻히지 않는다. 길이 점검은 아직 사람과 주석에 의존하고 자동 검사는 없다.
**코드** `unfollow_guard_service.py` — 유료 구독 유효 시 409 · `ref_type_length_guard.py` — 컬럼 정의의 사고 기록, 축약된 값, 삼키지 않는 환불

## 지금 기준
결제는 클라이언트 값을 믿지 않고 스토어 API 로 검증한 뒤에만 지급한다. 스토어 알림은 신호로만 쓰고 원본을 재조회하며, 주문 ID unique 와 만료일 기준 dedup 으로 재전송 · 동시 요청을 막는다. 크레딧은 원장 1행에 변동 후 잔액과 참조를 남기고, 차감은 조건부 UPDATE 한 문장, 복합 정산은 행 잠금으로 직렬화한다. 환불은 알림보다 먼저 커밋하고 실패를 삼키지 않으며, 짧은 문자열 컬럼은 정의 옆에 상한을 적어 둔다.
