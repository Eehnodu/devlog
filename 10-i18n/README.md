# 10. 다국어 처리의 변천

관리자가 카테고리에 언어를 고정하던 챗봇에서, 등록 시점에 30개 언어를 미리 번역해 두는 전시 안내와 20개 언어의 번역 상태를 관리하는 팬 플랫폼까지 온 과정이다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.03 | AI 상담 챗봇 서비스 | 답변 언어를 관리자가 카테고리 컬럼 하나에 고정 |
| 2 | 2025.03~04 | AI 상담 챗봇 서비스 | 고객이 위젯에서 언어를 고르고 요청마다 함께 보낸다 |
| 3 | 2026.03~04 | 전시관 AI 안내 서비스 | 등록 시 Celery 워커가 30개 언어를 구조화 출력으로 사전 번역 · 저장, 조회는 저장분 |
| 4 | 2026.06~08 | 팬 플랫폼 서비스 | 언어별 번역 행에 대기 · 완료 · 실패 상태, 실패 시 GPT 재번역 폴백, 언어별 템플릿 |

## 1. 관리자 고정 언어  →  `1-admin-fixed-language/`
**어디서** AI 상담 챗봇 서비스 · 2025.03
**문제** 위젯이 고객사 페이지에 iframe 으로 들어가는 구조라, 그 페이지의 방문자 언어를 관리자가 미리 정해 두는 발상으로 시작했다. 카테고리 행에 언어 컬럼을 하나 추가해 시스템 프롬프트에 끼웠다. 그런데 같은 카테고리를 영어 고객과 일본어 고객이 함께 쓰면 한쪽은 틀린 언어로 답을 받았다.
**바꾼 것** 이 단계에서는 컬럼을 추가한 것이 전부였다. 언어가 카테고리의 속성이 아니라 대화의 속성이라는 것을 다음 단계에서 깨달았다.
**결과** 카테고리를 언어별로 복제해 운영하는 임시 대응이 생겼고, 관리 항목이 늘었다.
**코드** `category_model.py` — 카테고리 행에 언어 컬럼을 추가한 마이그레이션과 모델

## 2. 요청 단위 언어  →  `2-per-request-language/`
**어디서** AI 상담 챗봇 서비스 · 2025.03~04
**문제** 한 카테고리가 여러 언어의 방문자를 상대해야 했다.
**바꾼 것** 위젯에 언어 선택 상자를 두고 선택값을 매 요청 본문에 함께 보낸다. 서버는 카테고리 컬럼 대신 요청 파라미터를 읽어 시스템 메시지에 끼운다. 고정 컬럼은 남아 있지만 더는 읽지 않는다.
**결과** 카테고리 복제가 없어졋고, 같은 카테고리에서 방문자마다 다른 언어로 답한다. 번역은 여전히 매 요청 모델 호출에 맡기는 구조라 콘텐츠가 많아지는 서비스에는 쓸 수 없었다.
**코드** `chat_view.py` — 요청 파라미터의 언어를 시스템 메시지에 끼우는 뷰 / `lang_select.js` — 선택값을 전역에 두고 매 요청에 실어 보내는 위젯 스크립트

## 3. 사전 번역  →  `3-pre-translation/`
**어디서** 전시관 AI 안내 서비스 · 2026.03~04
**문제** 작품 설명을 관람객이 언어를 바꿀 때마다 번역하면 매번 수 초의 지연과 비용이 붙는다. 언어가 30개라 한 번에 한 언어씩 호출하면 등록 한 건에 호출 30번이다.
**바꾼 것** 콘텐츠를 등록하면 관리자 화면은 즉시 응답하고, Celery 태스크가 언어를 묶음으로 나눠 번역한다. 한 호출에 여러 언어를 JSON 스키마(언어 코드 → 필드)로 구조화 출력하게 해 호출 수를 줄였고, 일시 오류만 재시도하고 빈 결과만 다시 채운다. 끝나면 Redis 캐시를 무효화하고, 누락분은 매일 자정 배치가 보충한다. 호출마다 사용량을 기록해 고객사별 원가를 남긴다. 프론트의 고정 문구(버튼 · 안내문)는 i18next 사전으로 두고 한국어만 번들에 넣은 뒤 나머지 언어는 선택 시점에 동적으로 불러온다.
**결과** 관람객은 언어를 고르면 저장분이 바로 나온다. 콘텐츠 번역은 서버 사전 번역, 화면 문구는 프론트 사전으로 역할이 갈렸다.
**코드** `gemini_trans_service.py` — 여러 언어를 한 호출에 구조화 출력, 재시도와 사용량 기록 / `trans_tasks.py` — 등록 시 묶음 번역 태스크, 빈 결과 재시도, 캐시 무효화 / `i18n.ts` — 고정 문구 사전과 동적 import

## 4. 번역 상태 관리와 폴백  →  `4-translation-state-pattern/`
**어디서** 팬 플랫폼 서비스 · 2026.06~08
**문제** 콘텐츠 · 뉴스 · 배너 · 프로모 · 공지 · 구독 상품처럼 번역 대상 도메인이 여섯을 넘었다. 번역이 일부 언어에서 실패하면 어느 행이 비었는지 알 수 없었고, 1차 번역기가 지원하지 않는 언어도 있었다. 한국어 조사 처리용 변수가 다른 언어 번역에 그대로 복사되어 화면에 노출되는 버그도 있었다.
**바꾼 것** 언어별 번역 행에 대기 · 완료 · 실패 상태 컬럼을 두었다. 등록 시 전 언어를 대기로 만들고 워커가 언어마다 완료 · 실패로 바꾸며, 관리자 화면은 그 상태로 "번역 중 / 실패 → 재번역"을 보여 준다. 같은 패턴을 여섯 도메인에 반복 적용했다. 1차 번역기의 결과가 비었거나 원문이 그대로 돌아오면 GPT 로 재번역하는 폴백을 두고, 폴백 판정은 언어 코드가 아니라 결과로 한다. 결과는 텍스트와 언어를 키로 Redis 에 캐시한다. 푸시 문구는 언어별 템플릿으로 나누고, 호칭 · 조사처럼 특정 언어에만 있는 요소는 그 언어 템플릿 안에서만 다룬다. 한국어 조사는 이름의 받침을 보고 고른다.
**결과** 실패한 언어만 다시 돌릴 수 있고, 어떤 언어로도 빈 화면이 나가지 않는다. "특정 언어에만 있는 변수는 그 언어에만" 이 원칙으로 남았다.
**코드** `translation_status_task.py` — 상태 컬럼과 언어별 완료 · 실패 갱신 워커 / `translator_fallback_service.py` — 결과 기준 폴백 판정과 캐시 / `push_text_localize.py` — 언어별 템플릿과 한국어 조사 처리

## 지금 기준
콘텐츠 번역은 등록 시점에 워커가 만들어 저장하고, 조회는 저장분만 준다. 번역 행마다 상태를 두어 실패를 보이게 하고 재번역할 수 있게 한다. 1차 번역기 실패는 결과로 판정해 GPT 폴백을 탄다. 화면 고정 문구는 프론트 사전이 맡고, 언어 고유 요소(호칭 · 조사)는 그 언어 템플릿 안에서만 처리한다. 언어를 매 요청 모델에 맡기는 2단계 방식은 콘텐츠가 적은 챗봇 답변에만 쓴다.
