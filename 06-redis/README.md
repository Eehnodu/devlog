# 06. Redis 용도의 고도화

대화 세션을 서버 프로세스의 딕셔너리에 두던 것에서 시작해, Redis 세션 저장소 → 응답 캐시 · 커넥션 공유 · Pub/Sub → 다중 워커 중복 실행을 막는 분산 락으로 쓰임이 넓어졌다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.05~07 | AI 아바타 모의 면접 서비스 | 대화 세션을 라우터 모듈의 전역 딕셔너리에 |
| 2 | 2025.11~2026.01 | AI 캐릭터 대화 서비스 | WebSocket 세션을 Redis 해시에, TTL 3600초 |
| 3 | 2026.03~ | 전시관 AI 안내 서비스 | 응답 캐시(10일) · 앱 전체가 공유하는 클라이언트 하나 · Pub/Sub 으로 SSE 중계 |
| 4 | 2026.05~ | 팬 플랫폼 서비스 | 배치 회차 잠금(SET NX + TTL) · 렌더 중복 방지 · 판정 · 번역 캐시 |
| 5 | 2026.04~ | 풀스택 베이스 템플릿 | 자료구조별 최소 메서드 + 분산 락을 가진 공통 서비스 |

## 1. 인메모리 딕셔너리  →  `1-in-memory/`
**어디서** AI 아바타 모의 면접 서비스 · 2025.05~07
**문제** 대화 이력을 라우터 파일의 전역 딕셔너리에 세션 ID 로 담았다. 재배포하면 진행 중인 대화가 전부 사라졌고, 워커를 둘로 늘리자 요청이 어느 워커에 닿는지에 따라 같은 사용자가 "이전 대화가 없는" 상태를 번갈아 만났다. 만료도 없어 프로세스가 살아 있는 동안 메모리가 계속 늘었다.
**바꾼 것** 이 시점에는 워커를 하나로 고정하는 것으로 넘어갔다. 이 시기 챗봇들은 Redis 를 쓰지 않았고, 세탁 서비스 앱만 Celery 브로커 용도로 Redis 를 두고 있었다.
**결과** 단일 워커라 동작은 했지만, 재배포 시 소실과 확장 불가라는 한계가 그대로 남아 다음 프로젝트에서 세션 저장소를 밖으로 빼는 계기가 되었다.
**코드** `session_store_dict.py` — 전역 딕셔너리에 세션을 만들고 이력을 덧붙이는 라우터와 서비스

## 2. Redis 세션 저장소  →  `2-session-store/`
**어디서** AI 캐릭터 대화 서비스 · 2025.11~2026.01
**문제** 음성 대화가 WebSocket 한 연결 안에서 STT → 대화 생성 → TTS 로 이어지는데, 캐릭터 지침 · 요약 · 대화 이력을 프로세스 메모리에 두면 재연결이나 재배포 때 대화가 끊겼다.
**바꾼 것** 세션 하나를 Redis 해시 하나로 옮겼다. 지침 · 요약 · 이력(JSON 문자열) · 로그 ID 를 필드로 나눠 담고, 저장할 때마다 만료 시간 1시간을 다시 걸어 대화가 이어지는 동안만 살아 있게 했다. 서비스는 세션이 있으면 그대로 쓰고, 없을 때만 DB 에서 캐릭터 설정을 읽어 지침을 조립한다.
**결과** 재접속과 재배포에도 대화가 이어지고, 워커를 늘려도 세션이 공유된다. 다만 Redis 클라이언트를 서비스 프로바이더가 요청마다 새로 만들고 있어 연결이 계속 늘어나는 문제가 다음 프로젝트로 넘어갔다.
**코드** `redis_service.py` — 세션을 해시로 저장하고 만료를 연장하는 공통 서비스
**코드** `session_usage.py` — 세션이 있으면 재사용, 없으면 만들고, 턴마다 다시 저장하는 대화 서비스

## 3. 캐시 · 커넥션 공유 · Pub/Sub  →  `3-cache-and-pool/`
**어디서** 전시관 AI 안내 서비스 · 2026.03~
**문제** 관람객 앱이 전시마다 30개 언어의 작품 목록을 반복 조회해 같은 쿼리가 계속 DB 를 때렸다. 요청마다 새 Redis 클라이언트를 만들던 구조라 요청 수만큼 커넥션 풀이 생겼다. 또 휴대폰에서 올린 사진을 키오스크 화면에 바로 띄워야 하는데, 두 요청이 다른 워커에 떨어지면 프로세스 메모리로는 서로를 알 수 없었다.
**바꾼 것** Redis 서비스를 모듈 단위 인스턴스 하나로 만들어 라우터 · 서비스 · 워커가 전부 그것을 import 하게 했다. 클라이언트는 첫 접근 때 한 번 만들어지고 내부 커넥션 풀이 공유된다. 작품 목록 응답은 전시 · 언어 · 페이지를 키로 JSON 문자열째 10일간 캐시하고, 관리자가 작품을 고치면 패턴 삭제로 그 전시의 캐시를 한 번에 비운다. 휴대폰 → 키오스크 전달은 Redis Pub/Sub(채널에 발행하면 구독 중인 모든 프로세스가 받는 방식)으로 키오스크가 SSE 로 대기하고, 업로드 서비스가 채널에 발행한다. 구독 전에 발행이 끝난 경우를 위해 결과 키도 10분간 남긴다.
**결과** DB 조회가 캐시로 대부분 걸러지고, 커넥션 수가 일정해졌다. 워커가 몇 개든 실시간 전달이 된다.
**코드** `redis_service.py` — 모듈 단위 인스턴스 하나와 Pub/Sub · 패턴 삭제 메서드
**코드** `response_cache.py` — 조회 조건을 키로 삼는 응답 캐시와 수정 시 일괄 무효화
**코드** `pubsub_sse_relay.py` — 구독 측 SSE 라우터와 발행 측 업로드 서비스

## 4. 분산 락과 판정 · 번역 캐시  →  `4-distributed-lock/`
**어디서** 팬 플랫폼 서비스 · 2026.05~
**문제** 1분마다 도는 번역 보충 배치가 워커 여러 개에서 동시에 깨어나 같은 메시지를 두 번 번역했다. 앱이 이미지가 준비될 때까지 몇 초마다 목록을 다시 묻는데, 폴링마다 같은 렌더 작업이 큐에 쌓여 같은 그림을 수십 번 그렸다. 별개로, Celery 태스크 안에서 웹 서버용 전역 Redis 클라이언트를 그대로 쓰니 두 번째 태스크부터 죽은 이벤트 루프의 커넥션을 잡아 조용히 실패했다.
**바꾼 것** 배치는 시작할 때 "키가 없을 때만 저장" 옵션으로 잠금 키를 쓰고, 실패하면 이번 회차를 건너뛴다. 잠금은 명시적으로 풀지 않고 TTL 로 자동 해제해 워커가 죽어도 다음 회차가 이어받는다. 렌더는 조합별 키가 있으면 큐에 넣지 않고 3분 뒤 자동 해제된다. Redis 가 죽어 있으면 잠금 없이 진행한다(중복 렌더보다 자료가 안 뜨는 쪽이 더 나쁘다). 워커에서는 태스크마다 새 커넥션을 열고 닫는 컨텍스트 매니저를 따로 두었다. 유해 발화 판정과 관리자 열람용 번역은 문장 해시를 키로 캐시하고, Redis 오류는 "캐시 없음" 으로 취급해 서비스가 멈추지 않게 했다.
**결과** 중복 번역 · 중복 렌더가 사라졌고, 워커의 Redis 실패가 없어졌다. 외부 분류기 · 번역기 호출 비용이 줄었다.
**코드** `redis_conn.py` — 웹 서버용 전역 클라이언트와 워커용 1회성 커넥션의 분리
**코드** `duplicate_guard.py` — 배치 회차 잠금과 렌더 중복 방지 키
**코드** `verdict_and_translation_cache.py` — 판정 · 번역 결과를 해시 키로 캐시, 실패는 무시

## 5. 베이스 템플릿의 공통 서비스  →  `5-base-template/`
**어디서** 풀스택 베이스 템플릿 · 2026.04~
**문제** 프로젝트마다 Redis 래퍼를 새로 쓰면서 메서드 이름과 TTL 기본값이 달라졌다.
**바꾼 것** 문자열 · 해시 · 집합 · 락의 최소 메서드만 가진 공통 서비스를 템플릿에 넣고, 어떤 용도에 어떤 자료구조를 쓰는지 주석으로 남겼다. 서비스 프로바이더가 요청 시점에 lazy 로 만들어 주입한다.
**결과** 새 프로젝트는 이 파일을 그대로 쓰고, 세션 · 캐시 · Pub/Sub 같은 도메인 메서드만 덧붙인다.
**코드** `redis_service.py` — 자료구조별 최소 메서드와 분산 락을 가진 공통 서비스

## 지금 기준
베이스 템플릿의 Redis 서비스가 출발점이다. Redis 는 DB 가 아니라 캐시 · 상태 · 동시성 제어에만 쓴다.
세션은 해시 + TTL, 캐시는 조회 조건을 전부 키에 넣고 수정 시 패턴 삭제로 무효화한다.
다중 워커에서 한 번만 돌아야 하는 일은 "키가 없을 때만 저장" + TTL 자동 해제로 막고, Redis 장애는 "캐시 없음 · 잠금 없음" 으로 넘겨 서비스가 멈추지 않게 한다.
Celery 워커에서는 웹 서버의 전역 클라이언트를 쓰지 않고 태스크마다 커넥션을 새로 연다.
Celery 브로커 전용 사용(세탁 서비스 앱, 2025.02)은 이 흐름과 별개로 가장 먼저 있었다.
