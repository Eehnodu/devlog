# 07. 배치 · 스케줄러의 변천

서버 크론이 독립 스크립트를 돌리던 것에서 시작해, 웹 프로세스 안의 APScheduler → 반복은 Celery Beat · 1회성 예약은 APScheduler → Celery Beat 를 표준으로 굳혔다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.05 | AI 상담 챗봇 서비스 | 서버 crontab 이 3일마다 Django 를 직접 초기화하는 스크립트 실행 |
| 2 | 2025.02~03 | 세탁 서비스 앱 | Django 앱 시작 시 APScheduler 스레드 → 워커 수만큼 중복 실행 |
| 3 | 2025.03~04 | 세탁 서비스 앱 | 반복 = Celery Beat(DB 스케줄러), 1회성 예약 = APScheduler date 트리거 + 작업 ID 저장 |
| 4 | 2026.03~ | 전시관 AI 안내 서비스 · 팬 플랫폼 서비스 | Celery Beat 를 코드에 선언, 매일 자정 누락분 보충, 커밋 후 큐 적재 |

## 1. 서버 크론 + 독립 스크립트  →  `1-cron-script/`
**어디서** AI 상담 챗봇 서비스 · 2025.05
**문제** 카테고리 챗봇끼리 대화를 시뮬레이션해 학습 데이터를 쌓는 작업이 필요했다. 한 번에 몇 분씩 걸리고 3일에 한 번이면 충분해서 웹 서버 안에 둘 이유가 없었다.
**바꾼 것** Django 를 직접 초기화하는 스크립트를 하나 만들고 서버 crontab 에 3일마다 자정으로 걸었다. 표준 출력을 텍스트 파일에 이어 붙여 실행 기록으로 삼았다. 로컬과 서버의 프로젝트 경로가 달라 경로 지정 줄 두 개를 배포할 때마다 주석으로 바꿔 넣었다.
**결과** 웹 서버와 완전히 분리돼 장애가 서로 번지지 않았다. 대신 크론 설정이 서버에만 있어 코드 저장소에서 보이지 않고, 실패해도 알 길이 파일을 열어 보는 것뿐이었다.
**코드** `self_learning_batch.py` — 경로 주석 토글, Django 초기화, crontab 한 줄이 함께 있는 독립 스크립트

## 2. 웹 프로세스 안의 APScheduler  →  `2-apscheduler/`
**어디서** 세탁 서비스 앱 · 2025.02~03
**문제** 72시간 응답 없는 품목 자동 처리, 매장 정보 갱신 같은 반복 작업을 앱 안에서 돌리려고 APScheduler 를 썼다. Django 앱이 준비되는 시점에 백그라운드 스레드로 스케줄러를 띄우는 구조였다. 운영에서 워커 프로세스를 여러 개 두자 프로세스마다 스케줄러가 하나씩 떠서 같은 작업이 워커 수만큼 돌았다.
**바꾼 것** 스케줄러만 따로 띄우는 관리 명령을 만들어 봤지만 반복 작업이 여전히 웹 코드와 같은 프로세스 모델 안에 있었다.
**결과** 이 구조로는 "정확히 한 번" 을 보장할 수 없다는 것이 분명해져 다음 단계에서 반복 작업을 통째로 옮겼다.
**코드** `scheduler_startup.py` — 앱 준비 시점에 스레드로 스케줄러를 띄우는 초기 구조와 그 한계 주석

## 3. Celery Beat + APScheduler 1회성 예약  →  `3-celery-beat-plus-apscheduler/`
**어디서** 세탁 서비스 앱 · 2025.03~04
**문제** 반복 작업은 한 곳에서만 시각을 재야 했고, 관리자가 "이 날 이 시각에 이 사람들에게" 예약하는 푸시 알림은 등록 · 취소 · 수정이 되어야 했다. 두 요구가 성격이 달랐다.
**바꾼 것** 반복 작업은 Celery Beat 로 옮겼다. Beat 프로세스 하나만 시각을 재고 실행은 워커가 맡으니 워커가 몇 개든 한 번만 돈다. 주기는 DB 스케줄러에 관리 명령으로 등록해 코드 배포 없이 켜고 끌 수 있게 했다. Redis 는 이 프로젝트에서 Celery 브로커 전용이었다. 1회성 예약은 APScheduler 의 date 트리거로 남겼다. 등록할 때 만든 작업 ID 를 예약 행에 함께 저장해 취소는 그 ID 로 잡을 지우고, 수정은 지운 뒤 같은 ID 로 다시 등록한다.
**결과** 반복 작업 중복이 사라졌고 예약 푸시를 관리자 화면에서 다룰 수 있게 됐다. 다만 스케줄러 두 종류가 공존해 운영 시 볼 곳이 둘이었다.
**코드** `celery_beat_tasks.py` — Celery 앱 설정, 반복 태스크, DB 스케줄러 등록 명령
**코드** `one_time_job.py` — date 트리거 등록과 작업 ID 저장 · 취소 · 수정 뷰

## 4. Celery Beat 표준  →  `4-celery-beat-standard/`
**어디서** 전시관 AI 안내 서비스(2026.03~) · 팬 플랫폼 서비스(2026.05~)
**문제** 작품 등록 시 30개 언어 음성 합성을 워커에 맡기는데, 외부 합성 API 가 같은 입력에도 간헐적으로 실패해 누락이 생겼다. 요청 경로에서 큐에 넣는 순서를 잘못 잡으면 DB 행이 확정되기 전에 워커가 먼저 깨어나 행을 못 찾을 수 있었다.
**바꾼 것** Beat 스케줄을 DB 대신 코드에 선언해 저장소에서 바로 보이게 했다. 매일 자정 도는 스캔 태스크는 음성이 빠진 행만 찾아 건별 합성 태스크를 다시 큐에 넣고, 실제 작업은 등록 직후에 쓰는 것과 같은 태스크가 맡는다. 워커의 DB 는 태스크마다 엔진을 새로 만들어 쓰고 닫는다(웹 서버 엔진은 그 프로세스의 이벤트 루프에 묶여 있어 공유하면 두 번째 실행부터 실패한다). 요청 경로는 "대기" 상태의 행을 먼저 커밋한 뒤 큐에 넣는다. 큐 적재가 실패해도 대기 행이 남아 보충 배치가 주워 간다. 워커 옵션에는 20건마다 재시작, 메모리 상한, 완료 후 ack 같은 이유를 주석으로 남겼다. 팬 플랫폼 서비스는 같은 설정 파일에 초 단위 간격형 스케줄(예약 공지 발송 · 미소비 구매 재시도 · 번역 보충)을 두고, 회차 겹침은 Redis 잠금으로 막는다(06 폴더 4단계).
**결과** 실패한 작업이 다음 날 자동으로 채워지고, 스케줄이 코드 리뷰 대상이 됐다. APScheduler 는 더 쓰지 않는다.
**코드** `celery_app.py` — 워커 옵션의 이유 주석과 자정 · 매시 Beat 스케줄
**코드** `sweep_missing_audio_task.py` — 태스크 전용 DB 세션, 건별 태스크, 누락분 스캔 태스크
**코드** `dispatch_after_commit.py` — 대기 행 커밋 후 큐 적재, 실패 시 배치가 회수

## 지금 기준
반복 작업은 Celery Beat 하나로 통일하고, 스케줄은 코드에 선언한다. Beat 프로세스는 반드시 하나만 띄우고 워커는 별도 systemd 유닛으로 늘린다.
큐에 넣는 쪽은 DB 상태(대기)를 먼저 커밋하고, 워커는 그 상태를 보고 처리 · 실패로 바꾼다. 실패분은 주기 배치가 다시 주워 가도록 설계해 단발 실패가 누락으로 남지 않게 한다.
워커의 DB · Redis 연결은 웹 서버와 공유하지 않고 태스크마다 새로 열고 닫는다.
관리자가 지정한 1회성 예약은 Beat 가 1분마다 도는 "발송 시각 지난 대기 건" 조회로 처리해, 별도 스케줄러 없이 같은 흐름에 얹는다.
