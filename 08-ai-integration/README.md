# 08. AI 연동의 변천

관리형 어시스턴트(Assistants API + Vector Store)에 답변을 통째로 맡기던 방식에서, 스트리밍 · 프롬프트 분리 · 도구 호출 · 원가 기록까지 서버가 직접 통제하는 방식으로 바뀌었다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.03 | AI 상담 챗봇 서비스 | Assistants API + Vector Store. 파일 업로드 → 임베딩 폴링 → file_search 어시스턴트, 외부 자원 ID 를 DB 에 저장 |
| 2 | 2025.05 | AI 상담 챗봇 서비스 | FastAPI 로 대화만 분리. Responses API + file_search 를 SSE 로 스트리밍, 끝나면 2차 정제 호출 |
| 3 | 2025.08 | AI 글쓰기 검토 서비스 | 관점별 프롬프트를 DB 에 두고 한 단계씩 순차 실행, 항목별 전체 수정본 JSON → diff |
| 4 | 2026.08 | 복지관 ERP | 도구 호출 19종 + 자유 SELECT 도구. SQL 은 화이트리스트 4중 검사. OpenAI · Claude 동일 인터페이스 |
| 5 | 2026.08 | 전시관 AI 안내 서비스 | 사용량 테이블(모델 · 토큰 · 음성 초 · 호출 수), 판정은 온도 0 별도 호출, 콘텐츠 해시로 변경 감지 |

## 1. 어시스턴트와 벡터 스토어  →  `1-assistants-vector-store/`
**어디서** AI 상담 챗봇 서비스 · 2025.03
**문제** 관리자가 올린 PDF · 문서를 근거로 답하는 챗봇을 며칠 안에 납품해야 했다. 검색 인덱스를 직접 만들 여유가 없었고, 문서 파싱과 벡터 검색을 모두 외부에 맡기는 것이 유일한 선택지였다.
**바꾼 것** 관리자가 파일을 올리면 서버가 Vector Store 를 만들고, SDK 의 폴링 호출로 임베딩이 끝나기를 기다린 뒤 file_search 도구가 붙은 어시스턴트를 만들었다. 어시스턴트 · 벡터 스토어 · 파일 ID 세 가지를 카테고리 행에 저장해 두고, 카테고리를 지울 때는 외부 자원을 먼저 지우고 성공했을 때만 DB 행을 지웠다. 대화는 스레드를 만들어 실행 스트림을 받았는데 WSGI 동기 뷰라 청크를 세션에 적재하고 클라이언트가 폴링으로 읽었다. 답변 끝에 붙는 출처 각주는 전각 괄호 형태여서 처음에 아스키 괄호로 잘못 잡아 그대로 노출됐고, 정규식을 전각 괄호로 고쳐 후처리했다.
**결과** 문서 기반 답변이 며칠 안에 동작했다. 대신 청크마다 세션 DB 쓰기가 생기고 워커가 점유됐으며, 어시스턴트의 지침 · 모델을 외부 상태로 관리해야 해서 바꿀 때마다 업데이트 호출이 필요했다.
**코드** `vector_store_admin.py` — 업로드 → 폴링 → 어시스턴트 생성, 삭제는 외부 자원 먼저 · `assistant_thread_chat.py` — 스레드 실행 스트림을 세션에 적재, 전각 괄호 각주 제거 · `category_model.py` — 외부 자원 ID 3종을 한 행에

## 2. Responses API 스트리밍  →  `2-responses-api-streaming/`
**어디서** AI 상담 챗봇 서비스 · 2025.05
**문제** 폴링 방식은 한 글자씩 보이는 것처럼 흉내만 냈고, 청크마다 DB 를 쓰느라 동시 접속 몇 명에도 워커가 막혔다. 어시스턴트 상태를 외부에서 관리하는 것도 번거로웠다.
**바꾼 것** 관리자 화면은 Django 에 두고 대화 응답만 FastAPI(ASGI) 로 분리했다. Responses API 에 file_search 도구를 붙여 스트림으로 받고, 조각이 오는 대로 SSE 이벤트로 흘려보냈다. 파일이 없는 카테고리는 같은 호출에 도구만 빼서 처리했다. 스트림이 끝나면 정리된 전문을 Chat Completions 로 한 번 더 보내 링크를 끝으로 모으는 형식 정제를 했다. 지침 · 모델은 어시스턴트가 아니라 요청마다 서버가 조립해 넘겼다.
**결과** 진짜 스트리밍이 됐고 어시스턴트 업데이트 호출이 사라졐다. 세션은 아직 프로세스 메모리여서 워커 1개 전제였고, 2차 정제 호출이 응답 완료를 한 번 더 늦췄다.
**코드** `sse_stream_router.py` — 도구 유무만 다른 같은 호출, SSE 조각 전송, 끝나면 정제 호출

## 3. 프롬프트 파이프라인  →  `3-prompt-pipeline/`
**어디서** AI 글쓰기 검토 서비스 · 2025.08
**문제** 필수 정보 · 관련성 · 문법 · 어조를 한 프롬프트로 한 번에 검토하게 하면 결과가 길고 뒤섞여 어느 규칙 때문에 고쳤는지 알 수 없었다. 검토 기준은 고객이 수시로 바꾸고 싶어 했다.
**바꾼 것** 관점별 프롬프트를 관리자가 DB 에 등록하고 순서를 정하게 했다. 프론트가 단계 번호와 프롬프트 ID 를 들고 한 단계씩 호출하면, 서버는 이전 단계가 고친 결과를 입력으로 삼아 다음 프롬프트를 실행한다. 출력은 항목별 전체 수정본을 JSON 배열로 강제하고, 모델이 순서를 바꿔도 입력 순서로 되돌린 뒤 저장한다. 원문과의 차이는 조회 시점에 diff 라이브러리로 계산해 하이라이트로 보여 준다.
**결과** 어느 관점이 어디를 고쳤는지 단계별로 남았고 기준 변경은 프롬프트 수정으로 끝났다. 단계 수만큼 호출이 늘어 전체 검토 시간은 길어졌다.
**코드** `review_pipeline_service.py` — 한 단계 실행, JSON 형식 강제, 순서 복원, 마지막 단계 판정

## 4. 도구 호출과 SQL 화이트리스트  →  `4-tool-calling-whitelist-sql/`
**어디서** 복지관 ERP · 2026.08
**문제** 직원이 "이용중인 사람 중 이번 달 상담 없는 사람" 같은 질문을 자연어로 물으면 답해야 했다. 모든 조합을 정해진 도구로 만들 수 없었지만, AI 가 쓴 SQL 을 그대로 실행하는 것은 위험했다. 또 공급자 하나에 묶이면 가격 · 품질 변화에 대응할 수 없었다.
**바꾼 것** 인자를 스키마로 묶은 읽기 전용 조회 도구 19종을 두고, 그것으로 안 되는 교차 질문만 자유 SELECT 도구로 열었다. 자유 SELECT 는 실행 전에 네 가지를 검사한다 — 허용 표 목록에 있는 표만, 쓰기 · 구조 변경 · 시스템 스키마를 뜻하는 금지 단어 없음, 판정 점수 · 좌표 · 비밀번호 같은 금지 컬럼 없음, 세미콜론 없는 단일 문장. 거부 사유와 DB 오류는 모델에게 되돌려 고쳐서 다시 부르게 했다. 공급자는 OpenAI · Claude 두 클래스를 같은 메서드 시그니처로 감싸고, 설정값 하나로 서비스 프로바이더가 골라 주입한다. 파일 검색 지원 여부 같은 차이는 클래스 속성으로 드러내 호출부가 분기한다.
**결과** 교차 질문이 풀리면서도 조회 범위는 승인된 표 안에 머물렀다. 컬럼 오타는 DB 오류에 맡기므로 파서 없이도 유지가 쉬웠다. 두 공급자 사이 인용 구조 차이는 완전히 감추지 못해 출처 표시는 공급자별로 달랐다.
**코드** `chatbot_sql.py` — 4중 검사와 실행 · `chatbot_tools.py` — 도구 정의, enum 검증, 필터 없는 전체 건수 동봉 · `ai_provider.py` — 설정값으로 공급자 선택, 같은 시그니처의 두 구현

## 5. 원가 기록과 결정성  →  `5-cost-tracking-and-determinism/`
**어디서** 전시관 AI 안내 서비스 · 2026.08
**문제** 번역 · 음성 합성 · 자막 · 임베딩 호출이 고객사별로 얼마나 드는지 알 수 없었다. 대화 모델에 "멸종한 종이 몇 개냐" 같은 개수 질문을 맡기면 같은 질문에 3종 · 7종 · 10종이 번갈아 나왔다. 학습 데이터를 조금 고쳐도 전체를 다시 임베딩하고 있었다.
**바꾼 것** AI 호출 1건을 사용량 1행으로 쌓는 테이블을 만들었다 — 종류 · 모델 · 입출력 토큰 · 오디오 초 · 호출 수 · 언어 수. 어느 고객사의 어느 콘텐츠인지는 컨텍스트 변수로 태스크 진입점에서 한 번 지정해 공용 호출 함수가 읽게 했고, 금액은 저장하지 않고 조회 시점에 단가표를 곱했다. 기록은 전용 세션으로 커밋해 본 작업이 롤백돼도 남는다. 개수 · 열거 판정은 대화 모델에서 떼어 온도 0 · 사고 모드 끔 · JSON 출력의 짧은 호출로 분리하고, 대화 모델에는 확정된 목록과 개수만 넘겼다. 학습 데이터는 설명의 해시를 행에 저장해 바뀐 행만 다시 임베딩하고, 건수 + 해시 체크섬으로 메모리 캐시의 신선도를 판정했다.
**결과** 고객사별 월 원가가 화면에 나왔고 재생성 이력도 행으로 남았다. 개수 답이 고정됐다. 판정이 하나라도 실패하면 모델 판단으로 되돌리므로 완전한 결정성은 아니다.
**코드** `usage.py` — 사용량 모델, 컨텍스트 변수 귀속, 전용 세션 기록 · `verify_temperature_zero.py` — 온도 0 판정 호출과 묶음 병렬 처리 · `species_embedding_hash.py` — 해시로 변경 행만 재임베딩, 건수 + 체크섬 캐시 키

## 지금 기준
AI 호출은 `module/infra/` 아래 공급자별 서비스로 두고, 서비스 프로바이더가 설정값으로 골라 주입한다. 답변은 Responses API(또는 동등한 메시지 API) 를 스트리밍으로 받아 SSE 나 WebSocket 으로 흘리고, 후처리 · 판정 같은 정확도가 필요한 호출은 온도 0 의 별도 호출로 분리한다. 모델이 DB 를 만질 때는 도구 정의를 거치고, 자유 SQL 은 화이트리스트 검사를 통과한 SELECT 만 실행한다. 모든 호출은 사용량 행으로 남기고 금액은 조회 시점에 계산한다.
