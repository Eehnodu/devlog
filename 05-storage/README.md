# 05. 파일 저장의 변천

이미지를 DB 텍스트 컬럼에 base64 로 넣던 것에서 시작해, 서버 로컬 폴더 → S3 + CloudFront → 비동기 클라이언트 → 비공개 버킷 + 서명 URL 로 바뀌었다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.02~09 | 공공기관 상담 챗봇 · AI 상담 챗봇 서비스 | base64 문자열을 DB 컬럼에 · 로컬 media 폴더 + 내용 해시 파일명 |
| 2 | 2025.11~2026.01 | AI 캐릭터 대화 서비스 | S3 업로드 + CloudFront URL 조립, 다중 업로드 실패 시 롤백 |
| 3 | 2026.03~ | 전시관 AI 안내 서비스 | 동기 boto3 → aioboto3, 클라이언트 재사용 |
| 4 | 2026.05~ · 2026.08 | 팬 플랫폼 서비스 · 복지관 ERP | 버킷 설정 비면 로컬 폴백 · 비공개 버킷 + 열람 시 서명 URL(6시간) |

## 1. DB base64 와 로컬 폴더  →  `1-local-and-base64/`
**어디서** 공공기관 상담 챗봇 · AI 상담 챗봇 서비스 · 2025.02~09
**문제** 첫 챗봇은 파일 저장소라는 개념이 없었다. 관리자가 올린 프로필 이미지를 브라우저가 base64 문자열로 바꿔 보내고, 서버는 그 문자열을 텍스트 컬럼에 그대로 넣었다. 챗봇 정보를 조회할 때마다 이미지 전체가 JSON 응답에 실려 나가고, 행 하나가 수백 KB 가 되어 목록 조회까지 느려졌다.
**바꾼 것** 다음 챗봇부터는 파일을 서버의 media 폴더에 두고 DB 에는 파일명만 저장했다. 파일명은 내용 해시로 만들어 같은 이미지를 두 번 올려도 한 번만 저장되게 했고, 브라우저는 정적 경로로 직접 받았다.
**결과** DB 행이 가벼워지고 이미지 중복이 사라졌다. 대신 파일이 서버 디스크에 묶여 서버를 늘리거나 재배포할 때 옮겨 줘야 했고, 백업 대상도 두 곳이 되었다.
**코드** `profile_image_base64.py` — 이미지가 텍스트 컬럼과 JSON 응답에 통째로 들어가는 모델과 저장 뷰
**코드** `local_media_hashed_name.py` — 내용 해시로 파일명을 만들고 이미 있으면 저장을 건너뛰는 로컬 저장

## 2. S3 + CloudFront, 실패 시 롤백  →  `2-s3-cloudfront/`
**어디서** AI 캐릭터 대화 서비스 · 2025.11~2026.01
**문제** 캐릭터 파츠 이미지가 사용자마다 수십 장씩 쌓여 서버 디스크로는 감당이 안 됐다. 또 한 요청에서 파일 여러 개를 올리는데, 중간에 하나가 실패하면 DB 는 트랜잭션으로 되돌아가지만 이미 올라간 파일은 그대로 남아 고아 객체가 생겼다.
**바꾼 것** 저장은 S3, 열람은 CloudFront 도메인으로 분리했다. DB 에는 파일명만 두고 URL 은 사용자 · 자산 · 분류 규칙으로 매번 조립해 CDN 도메인이 바뀌어도 DB 를 고칠 일이 없게 했다. 업로드에 성공한 키를 리스트에 모아 두고, 예외가 나면 그 리스트를 돌며 S3 객체를 지우는 롤백을 넣었다.
**결과** 서버 디스크 의존이 사라지고 부분 실패가 남기는 쓰레기가 없어졌다. 다만 클라이언트가 동기 boto3 라서 업로드하는 동안 비동기 서버의 이벤트 루프가 멈추는 문제가 남았다.
**코드** `s3_service.py` — 동기 boto3 업로드 · 삭제와 CloudFront URL 조립
**코드** `asset_upload_rollback.py` — 성공한 키를 모아 두고 예외 시 되돌리는 다중 업로드

## 3. 비동기 클라이언트  →  `3-async-s3/`
**어디서** 전시관 AI 안내 서비스 · 2026.03~
**문제** 작품 이미지와 30개 언어 음성 파일을 올리는 동안 동기 업로드가 이벤트 루프를 잡아, 그 시간에는 다른 요청과 WebSocket 까지 전부 멈췄다. 서버가 잠깐씩 죽은 것처럼 보였다.
**바꾼 것** boto3 를 aioboto3 로 바꿔 업로드 · 삭제 · 복사를 전부 await 로 처리했다. 클라이언트는 첫 호출 때 한 번 열어 재사용하고 앱 종료 시 닫는다. 여러 서비스에 흩어져 있던 URL → 키 변환도 함수 하나로 모았다.
**결과** 업로드 중에도 다른 요청이 정상 처리된다. 버킷은 아직 공개 읽기라 URL 을 아는 사람은 누구나 열 수 있었다.
**코드** `s3_service.py` — aioboto3 세션 · 클라이언트 재사용과 오래된 객체 정리 배치

## 4. 비공개 버킷 + 서명 URL, 로컬 폴백  →  `4-private-bucket-signed-url/`
**어디서** 팬 플랫폼 서비스(2026.05~) · 복지관 ERP(2026.08)
**문제** 개발 PC 마다 S3 자격증명을 나눠 주는 것도, 로컬에서 실제 버킷에 테스트 파일을 쌓는 것도 부담이었다. 그리고 복지관 ERP 는 상담일지 첨부 · 이용자 서류처럼 개인정보가 담긴 파일을 다루는데, 공개 버킷이면 주소가 새는 순간 누구나 열 수 있다.
**바꾼 것** 환경별 버킷 값이 비어 있으면 로컬 디스크, 채워져 있으면 S3 로 저장하는 분기를 저장소 파사드 한 곳에 넣었다. 서비스는 상대 경로 문자열만 주고받고 그 경로가 DB 에 들어간다. 복지관 ERP 는 버킷을 비공개로 두고, 열람 요청마다 6시간짜리 서명 URL(시간이 지나면 열리지 않는 임시 주소)을 만들어 준다. 자격증명은 코드와 .env 에 두지 않고 서버 인스턴스 역할에서 가져간다. 파일명은 uuid 로 새로 만들어 한글 · 공백 · 경로 조작 문제를 한 번에 피했고, 브라우저가 파일을 바로 열 수 있도록 확장자별 Content-Type 을 못박았다.
**결과** 개발 환경은 설정 한 줄로 로컬에서 돌고, 운영은 주소가 새어도 시간이 지나면 열리지 않는다. 복지관 ERP 는 다시 동기 boto3 로 돌아가되 호출부가 별도 스레드로 감싸 이벤트 루프를 막지 않게 했다.
**코드** `s3.py` — 비공개 버킷에 대한 서명 URL 발급과 Content-Type 고정
**코드** `storage.py` — 버킷 설정 유무로 로컬 · S3 를 가르는 저장소 파사드
**코드** `local_fallback_settings.py` — 환경별 버킷 값이 비면 로컬로 떨어지는 설정과 저장 함수

## 지금 기준
베이스 템플릿에는 파일 저장 코드를 넣지 않았다. 프로젝트마다 파일의 성격이 달라 필요할 때 4단계의 저장소 파사드를 가져와 시작한다.
기준은 이렇다. 서비스는 상대 경로만 다루고, 저장 위치는 환경 설정의 버킷 값 하나로 갈린다. 파일명은 uuid, 원본 이름은 DB 에 따로 둔다.
개인정보가 담길 수 있는 파일은 비공개 버킷 + 서명 URL 이 기본이고, 공개 자산(배너 · 썸네일)만 CDN 공개 URL 을 쓴다.
클라이언트는 비동기(aioboto3)를 우선하되, 동기 클라이언트를 쓸 때는 반드시 별도 스레드로 감싼다. 여러 파일을 올리는 요청은 성공한 키를 모아 두고 실패 시 되돌린다.
