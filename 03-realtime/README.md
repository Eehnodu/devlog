# 03. 실시간 전송의 변천

동기 서버에서 세션 폴링으로 스트리밍을 흉내 내던 것에서 시작해, SSE 로 진짜 스트리밍을 하고, 용도별 WebSocket(상담원 핸드오프 · 음성 대화 · 실시간 통역 · 단체 방)으로 넓어졌다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.02 | AI 상담 챗봇 서비스 (초기 Django 계열) | OpenAI 청크를 Django 세션에 적재, 프론트가 100ms 폴링 |
| 2 | 2025.06 | AI 상담 챗봇 서비스 (Django + FastAPI 계열) | FastAPI 스트리밍 응답(text/event-stream), Responses API 델타 즉시 전송 |
| 3 | 2025.09 | AI 상담 챗봇 서비스 (Django + FastAPI 계열) | 상담원 핸드오프 3종 WebSocket, 방 ID 상태, 충돌 코드 4000, 대화 기록 행 잠금 |
| 4 | 2025.12 | AI 캐릭터 대화 서비스 | WebSocket 한 세션에서 PCM → STT → GPT → TTS, 바이너리 + JSON 프레임 |
| 5 | 2026.04~06 | 전시관 AI 안내 서비스 | PCM 큐 → Gemini Live, 번역 음성 · 원문 · 번역 전사 멀티플렉싱, 단체 방 asyncio 락 |
| 현재 | 2026.04~ | 풀스택 베이스 템플릿 | WebSocket 프로바이더 · 로그인 데코레이터 · 연결 매니저 |

## 1. 세션 폴링  →  `1-session-polling/`
**어디서** AI 상담 챗봇 서비스 (초기 Django 계열) · 2025.02
**문제** Django 를 동기 WSGI 로 돌리고 있어 답변을 조각 단위로 흘려보낼 방법이 없었다. 그런데 한 문장씩 나타나는 화면은 납품 요구사항이었다.
**바꾼 것** 메인 요청 뷰가 OpenAI 스트림을 받으면서 청크마다 누적 문자열을 Django 세션에 저장하고 강제 커밋했다. 프론트는 메인 요청을 보내 놓고 0.1초마다 별도 뷰를 불러 세션의 누적 문자열을 받아 마지막 말풍선을 갈아 끼웠다. 메인 요청이 끝나면 폴링을 멈추고 누적 문자열을 비웠다.
**결과** 화면은 스트리밍처럼 보였다. 대신 청크마다 세션 테이블에 쓰기가 한 번씩 일어났고, 메인 요청이 답변 내내 워커 하나를 붙잡았으며, 폴링 요청이 그 위에 초당 열 번씩 더 들어왔다. iframe 안에서는 세션 쿠키 자체가 문제가 되기도 했다.
**코드** `views.py` — 청크마다 세션 저장하는 메인 뷰와 세션을 읽어 돌려주는 폴링 뷰. `main.js` — 0.1초 간격 폴링과 종료 처리.

## 2. SSE 스트리밍  →  `2-sse/`
**어디서** AI 상담 챗봇 서비스 (Django + FastAPI 계열) · 2025.06
**문제** 폴링 방식은 DB 쓰기와 워커 점유가 비용이었다. 관리자 화면은 Django 에 남겨 두되 대화 응답만은 비동기 서버로 옮겨야 했다.
**바꾼 것** 대화 응답 생성을 FastAPI 로 떼어내고, 스트리밍 응답 객체에 비동기 제너레이터를 넘겨 text/event-stream 으로 내보냈다. Responses API 의 텍스트 델타가 오는 즉시 SSE 한 줄로 흘려보내고, 끝나면 종료 이벤트를 보낸다. 스트림이 끝난 뒤 출처 각주 제거와 링크 정리(2차 GPT 호출)를 하고 로그를 남긴다.
**결과** 세션 저장도 폴링도 없어졌고 연결 하나로 답변이 흘렀다. 대화 상태는 아직 프로세스 메모리 딕셔너리에 있어 워커를 늘리면 깨지는 구조였고, 이 문제는 뒤에 Redis 로 옮겨 풀었다.
**코드** `chatbot_router.py` — 델타를 즉시 SSE 로 내보내는 비동기 제너레이터와 스트리밍 응답.

## 3. 상담원 핸드오프 WebSocket  →  `3-websocket-handoff/`
**어디서** AI 상담 챗봇 서비스 (Django + FastAPI 계열) · 2025.09
**문제** 챗봇이 답하지 못하면 사람 상담원에게 넘겨야 했다. 사용자 · 상담원 양방향 대화, 상담원 대시보드의 대기 목록 실시간 갱신은 요청-응답 모델로는 안 됐다.
**바꾼 것** WebSocket 을 세 종류로 나눴다 — 상담원 대시보드(대기 방 목록 수신), 사용자 요청(방 생성 · 메시지), 상담원 입장(방 선택 · 메시지). 방 ID 를 사용자 세션과 챗봇 대화 로그 ID 로 만들어 세 소켓이 같은 딕셔너리로 상태를 공유한다. 다른 상담원이 이미 들어온 방에 또 들어오면 앱 정의 종료 코드 4000 으로 닫는다. 사용자 소켓과 상담원 소켓이 같은 대화 기록 행에 번갈아 이어 붙이므로 행을 읽을 때 SELECT FOR UPDATE 로 잠갔다.
**결과** 챗봇 대화에서 상담원 대화로 끊김 없이 넘어가고 기록도 한 행에 이어졌다. 한계도 분명했다 — 하트비트 · 재연결이 없고, 사용자 식별을 쿼리 파라미터로 했고, 방 상태가 프로세스 메모리라 단일 워커 전제였다.
**코드** `routes.py` — 사용자 · 상담원 입장 소켓과 방 상태 공유, 4000 종료. `chatbot_log.py` — 대화 기록 행 잠금.

## 4. 음성 대화 WebSocket  →  `4-websocket-voice/`
**어디서** AI 캐릭터 대화 서비스 · 2025.12
**문제** 캐릭터와 목소리로 대화해야 했다. 마이크 음성을 서버로 보내고, 인식된 문장 · 답변 자막 · 답변 음성 · 캐릭터 표정 정보를 한 흐름으로 돌려받아야 했다.
**바꾼 것** WebSocket 한 세션에서 바이너리 프레임과 텍스트 프레임을 구분해 받았다. 바이너리(PCM)는 버퍼에 쌓고, 말이 끝났다는 텍스트 신호가 오면 PCM 을 WAV 로 감싸 STT 에 넘기고, 인식 문장을 페르소나 GPT 에 보내고(대화 기록은 Redis 세션), 답변 텍스트를 TTS 로 합성한다. 답변 음성은 바이너리 프레임 하나로, 자막과 감정 메타는 JSON 프레임으로 같은 소켓에 보낸다. TTS SDK 의 동기 제너레이터는 스레드 실행기에서 조각을 모아 이벤트 루프를 막지 않게 했다. 소켓 인증은 핸드셰이크 쿠키로 했다.
**결과** 음성 한 턴이 소켓 왕복 한 번으로 끝났다. 연결 상태를 데이터클래스로 묶고 메시지 종류별 처리 함수로 나눠 이후 소켓 서비스의 기본 형태가 됐다.
**코드** `ws_service.py` — 바이너리 · JSON 프레임 분기와 STT → GPT → TTS 파이프라인. `gpt_service.py` — PCM → WAV → STT, TTS 조각 모아 단일 바이너리.

## 5. 멀티플렉싱과 단체 방  →  `5-websocket-multiplex/`
**어디서** 전시관 AI 안내 서비스 · 2026.04~06
**문제** 대면 통역은 말하는 동안 번역 음성이 바로 나와야 하고 원문 · 번역 자막도 함께 보여야 했다. 언어를 따로 감지하면 오탐이 잦았다. 단체 안내 방은 안내원 하나에 참여자 여럿이 붙어 여러 코루틴이 같은 방 상태를 고쳤다.
**바꾼 것** 클라이언트 PCM 을 큐에 넣고 별도 태스크가 Gemini Live 세션으로 흘려보내 수신과 송신 속도를 분리했다. 모델이 돌려주는 번역 음성은 바이너리 프레임, 원문 전사 · 번역 전사 · 턴 종료(토큰 사용량 포함) · 끼어들기는 JSON 프레임으로 한 소켓에 멀티플렉싱했다. 언어 감지는 "한국어면 대상 언어로, 아니면 한국어로" 규칙만 시스템 지시에 넣어 모델에 맡겼다. 유휴 세션을 서버가 끊는 경우는 복구 가능 코드로 분류해 사용자에게 내부 예외 문자열을 보이지 않게 했다. 단체 방은 방 딕셔너리를 만질 때마다 asyncio 락 안에서만 고치고, 소켓 닫기처럼 오래 걸리는 작업은 락 밖으로 뺐다. 안내원이 끊기면 10분 유예 뒤에 방을 정리하고, 그 안에 돌아오면 정리를 취소한다. 참여자 번호와 방 코드는 Redis 에 두어 워커가 여럿이어도 겹치지 않는다. 소켓 엔드포인트는 용도별로 여섯 개이며 HTTP 와 같은 프로바이더 · 로그인 데코레이터를 쓴다.
**결과** 통역은 말하는 도중에 번역 음성과 자막 두 줄이 함께 흘렀다. 단체 방은 접속 · 이탈 · 재접속이 겹쳐도 상태가 깨지지 않았다.
**코드** `gemini_live_service.py` — PCM 큐 → Gemini Live, 바이너리 · JSON 멀티플렉싱, 유휴 종료 처리. `docent_live_service.py` — asyncio 락으로 보호한 방 상태와 유예 정리. `web_socket_router.py` — 용도별 여섯 소켓과 데코레이터.

## 지금 기준
베이스 템플릿은 WebSocket 을 HTTP 와 같은 틀로 다룬다(`6-current-standard/`). 소켓 전용 프로바이더가 서비스를 지연 생성하고, 프로바이더 주입 데코레이터와 로그인 데코레이터(핸드셰이크 쿠키 검증)가 라우터에 붙는다. 연결 · 방 · 사용자 정보는 싱글턴 연결 매니저가 갖고 서비스는 방 단위 브로드캐스트만 부른다. 프레임은 바이너리(오디오)와 JSON(제어 · 자막)을 한 소켓에서 구분하고, 방 상태처럼 여러 코루틴이 만지는 것은 asyncio 락으로, 워커 사이에 공유해야 하는 것은 Redis 로 둔다. 단발 텍스트 스트리밍은 SSE, 양방향 · 음성 · 방은 WebSocket 을 쓴다.
