# 04. 로그 처리의 변천

print 와 systemd 저널에 의존하던 로그를, 파일 로깅 → 요청 단위 추적 → 목적별 전용 파일로 바꿔 온 과정이다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.02~04 | AI 상담 챗봇 서비스 (초기 Django 계열) | print 와 기본 logging 그대로. 표준 출력이 systemd 저널로 |
| 2 | 2025.09 | AI 글쓰기 검토 서비스 | 앱 로그를 파일 하나로. 요청/응답 미들웨어가 상태코드별 레벨로 한 줄 |
| 3 | 2026.04 | 풀스택 베이스 템플릿 · 복지관 ERP | ASGI 미들웨어가 요청마다 UUID → 컨텍스트 변수 → 로깅 필터가 모든 줄에 태깅 |
| 4 | 2026.03~ | 전시관 AI 안내 서비스 · 팬 플랫폼 서비스 | 연동 · 워커별 전용 로그 파일. 요청 ID 옆에 고객사 · 세션 · 사용자 컨텍스트 |

## 1. print 와 저널  →  `1-print-journal/`
**어디서** AI 상담 챗봇 서비스 (초기 Django 계열) · 2025.02~04
**문제** 로그 설정이 따로 없었다. 뷰 곳곳의 print 가 표준 출력으로 나가고, 그것이 systemd 저널에 쌓이는 것이 로그의 전부였다. 대화 전문과 세션 키 같은 값이 그대로 찍혀 운영 저널에 남았고, 요청이 겹치면 어느 줄이 어느 요청의 것인지 구분할 수 없었다. 저널은 용량 제한에 걸리면 오래된 것부터 사라져 며칠 전 장애는 되짚을 수 없었다.
**바꾼 것** 이 단계에서는 바꾸지 못했다. 며칠 단위로 납품하는 위젯이었고, 문제를 겪은 뒤 다음 프로젝트에서 로깅을 설정으로 끌어냈다.
**결과** "무엇을 남기고, 어디에, 얼마나 보관할지" 를 코드가 아니라 설정이 정해야 한다는 기준이 생겼다.
**코드** `views_chat.py` — 진입 · 인자 · 세션 값을 print 로 찍던 뷰 조각. 어디에 무엇이 남았는지가 보인다

## 2. 파일 로깅  →  `2-file-logging/`
**어디서** AI 글쓰기 검토 서비스 · 2025.09
**문제** 서버가 FastAPI 로 바뀌면서 Uvicorn 이 자기 로거를 들고 왔다. 그대로 두면 앱 로그와 서버 로그가 다른 형식으로 섞이고, 모듈마다 핸들러를 달면 같은 줄이 두 번 찍혔다. 요청이 어떻게 끝났는지는 접근 로그를 따로 뒤져야 알 수 있었다.
**바꾼 것** 앱 로그만 파일 하나로 모으고 자정마다 회전시켰다. 핸들러는 루트 로거에만 두고 모듈 로거는 전파만 하게 해서 중복을 없앴다. Uvicorn 로거는 핸들러를 우리 것으로 교체하고 전파를 끊었고, 접근 로거는 WARNING 이상만 남겼다(접근 기록은 Nginx 가 남긴다). 요청/응답 미들웨어를 하나 두어 요청마다 메서드 · 경로 · 상태코드 · 소요 시간을 한 줄로 찍고, 상태코드가 레벨을 정하게 했다(5xx 는 ERROR, 4xx 는 WARNING, 3xx 는 INFO 에 REDIRECT 표시).
**결과** 파일에서 ERROR 만 걸러도 서버 오류 목록이 나왔다. 그러나 여러 요청이 동시에 들어오면 줄들이 섞이는 문제는 그대로였다.
**코드** `logging_config.py` — 루트에만 핸들러, 일 단위 회전, Uvicorn 로거 교체 / `request_log_middleware.py` — 상태코드가 곧 레벨인 한 줄 요청 로그

## 3. 요청 ID 태깅  →  `3-request-id/`
**어디서** 풀스택 베이스 템플릿 · 복지관 ERP · 2026.04
**문제** 비동기 서버는 한 워커가 여러 요청을 번갈아 처리한다. 같은 시각에 찍힌 줄 열 개가 서로 다른 요청의 것일 수 있어, 장애 한 건을 처음부터 끝까지 따라가려면 추측이 필요했다. WebSocket 연결은 접근 로그에 한 줄만 남아 프레임 단위 문제는 추적할 수 없었다.
**바꾼 것** 순수 ASGI 미들웨어가 HTTP 와 WebSocket 요청마다 UUID 를 만들어 컨텍스트 변수에 넣는다. 컨텍스트 변수(contextvars)는 코루틴마다 값이 따로 유지되는 저장소라, 스레드 로컬처럼 코루틴 사이에서 값이 섞이지 않는다. 로깅 필터가 모든 record 에 그 값을 채워 넣어 어떤 모듈이 찍든 줄마다 요청 ID 가 붙고, HTTP 응답에는 x-request-id 헤더로 돌려주어 화면에서 본 오류를 로그와 바로 맞출 수 있다. 로드밸런서가 붙여 주는 ID 를 쓰지 않고 앱에서 만든 이유는 WebSocket 프레임까지 같은 ID 로 묶고, 인프라 설정 없이 어느 서버에서도 같게 동작하게 하려는 것이었다.
**결과** 오류 응답 헤더의 ID 하나로 그 요청이 남긴 줄 전부를 grep 할 수 있게 됐다. 앱은 표준 출력만 쓰고 파일 저장은 systemd 유닛에 맡기는 쪽으로 단순해졌다.
**코드** `request_id.py` — HTTP · WebSocket 모두 지나가는 ASGI 미들웨어와 응답 헤더 / `context.py` — 요청 ID 컨텍스트 변수 / `logging_config.py` — 필터가 모든 줄에 ID 를 붙이고 Uvicorn 로거를 루트로 전파

## 4. 목적별 분리  →  `4-purpose-split/`
**어디서** 전시관 AI 안내 서비스 · 팬 플랫폼 서비스 · 2026.03~
**문제** 외부 모델 호출, 푸시 발송, 영상 생성 워커, 방송 WebSocket 이 한 서버에 모이자 로그가 한 흐름에 섞였다. 한 번에 수십 장을 걸어 두는 생성 작업의 진행 로그가 웹 요청 로그를 덮었고, 여러 고객사가 같은 서버를 쓰는 전시관에서는 요청 ID 만으로는 "어느 고객사의 어느 세션" 인지 알 수 없었다.
**바꾼 것** 대량으로 쌓이는 로그는 연동 · 워커 · WebSocket 별 전용 파일로 보낸다. 로거 이름이 모듈 경로와 같다는 점을 이용해 이름으로 라우팅하고, 전용 로거는 루트로 전파하지 않아 콘솔에 다시 섞이지 않는다. 패키지 이름에 핸들러를 달면 하위 모듈이 전파로 걸리므로 파일이 늘어도 설정을 고치지 않는다. 파일을 못 열면(디렉터리 없음 · 권한) 핸들러를 만들지 않고 루트 콘솔로 폴백해 로깅 설정이 서버 기동을 막지 않게 했다. 컨텍스트도 늘렸다. 팬 플랫폼은 로그인 데코레이터에서 사용자 ID 를, 전시관은 WebSocket 진입에서 고객사 · 세션 ID 를 컨텍스트에 넣어 필터가 함께 태깅한다. 회전은 파이썬이 아니라 logrotate 가 맡고, systemd 가 붙여 쓰는 표준 출력 파일은 프로세스가 다시 열 수 없어 copytruncate 로 처리한다.
**결과** 장애가 나면 해당 연동의 파일 하나만 열어 보면 된다. 조회 구조가 필요한 기록(회원 활동 타임라인 등)은 파일이 아니라 DB 테이블로 보내는 기준도 함께 정해졌다.
**코드** `logging_config.py` — 이름 라우팅 · 전파 끔 · 콘솔 폴백 / `context_extended.py` — 고객사 · 세션 컨텍스트 변수와 실제 세팅 지점 / `logrotate.conf` — 전용 파일과 표준 출력 파일을 다르게 회전

## 지금 기준
베이스 템플릿은 3단계가 기본이다. ASGI 미들웨어가 요청 ID 를 만들고, 필터가 모든 줄에 붙이고, 응답 헤더로 돌려준다. 앱은 표준 출력만 쓰고 파일 저장 · 회전은 systemd 유닛과 logrotate 가 맡는다. 연동이나 워커가 붙어 로그가 많아지면 4단계처럼 로거 이름으로 전용 파일을 추가하고, 사용자 · 고객사 같은 컨텍스트는 컨텍스트 변수와 필터에 한 줄씩 더한다. print 는 기동 · 종료 메시지 외에는 쓰지 않는다.
