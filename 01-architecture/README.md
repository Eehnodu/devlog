# 01. 백엔드 구조의 변천

뷰 파일 하나에 모든 로직을 넣던 Django 프로젝트에서 시작해, 도메인 단위 모듈과 의존성 주입으로 정리된 FastAPI 템플릿까지 다섯 단계로 바뀌었다.

## 흐름
| 단계 | 시기 | 프로젝트 | 방식 |
|---|---|---|---|
| 1 | 2025.02 | AI 상담 챗봇 서비스 (초기 Django 계열) | 뷰 함수에 요청 처리 · AI 호출 · DB 저장 직접. 외래키 없음 |
| 2 | 2025.04 | AI 상담 챗봇 서비스 (초기 Django 계열) | 파일 ID 컬럼 → JSON 배열, 버튼 메뉴를 자기참조 외래키 트리로 |
| 3 | 2025.06 | AI 상담 챗봇 서비스 (Django + FastAPI 계열) | 관리자 화면은 Django, 응답 생성은 FastAPI. 같은 테이블을 두 ORM 이 정의 |
| 4 | 2025.08 | AI 글쓰기 검토 서비스 | 라우터 · 서비스 · 저장소 3계층, 전 테이블 외래키, Alembic |
| 5 | 2026.04~ | 풀스택 베이스 템플릿 · 복지관 ERP | 도메인 4파일 모듈 + 공통 코어 + 서비스 프로바이더 |

## 1. Django 평면 구조  →  `1-django-flat/`
**어디서** AI 상담 챗봇 서비스 (초기 Django 계열) · 2025.02
**문제** 고객사 홈페이지에 붙일 상담 위젯을 며칠 안에 납품해야 했다. 뷰 함수 하나가 요청을 풀고, OpenAI 를 부르고, 세션을 만지고, 로그를 저장했다. 모델은 한 파일에 몰려 있었고 테이블 사이에 외래키가 없어서 카테고리와 로그는 이름 문자열로만 이어졌다. 학습 파일이 몇 개 올라올지 몰라 파일 ID 컬럼을 20개 나열했고, 대화 로그는 텍스트 한 칸에 계속 이어 붙였다.
**바꾼 것** 이 단계에서는 바꾼 것이 없다. 처음 만든 구조 그대로다.
**결과** 납품은 됐지만 카테고리를 지우면 로그가 고아가 됐고, 기능을 하나 고치려면 500줄짜리 뷰 파일을 뒤져야 했다.
**코드** `models.py` — 파일 ID 컬럼 20개와 문자열 연결 로그 모델. `views.py` — 요청 파싱 · AI 호출 · 로그 저장이 한 함수에 있는 뷰.

## 2. 스키마 정리  →  `2-schema-cleanup/`
**어디서** AI 상담 챗봇 서비스 (초기 Django 계열) · 2025.04
**문제** 같은 챗봇을 다른 고객사에 몇 번 더 납품하면서 파일 ID 컬럼 나열과 뷰 코드 안에 JSON 으로 하드코딩된 버튼 시나리오가 매번 발목을 잡았다. 버튼 문구 하나를 바꾸려면 코드를 수정해 재배포해야 했다.
**바꾼 것** 파일 ID 20개 컬럼을 JSON 배열 컬럼 하나로 합치고, 쓰지 않는 복제 테이블을 없앴다. 버튼 시나리오는 부모 버튼 ID 를 참조하는 테이블로 옮겼다. 이 자기참조 외래키가 이 프로젝트 계열의 첫 외래키였고, 상위 버튼을 지우면 하위 트리가 함께 지워지도록 CASCADE 를 걸었다.
**결과** 관리자가 버튼 트리를 화면에서 편집할 수 있게 됐다. 다만 대화 로그는 여전히 이름 문자열 연결과 텍스트 누적 방식이었다.
**코드** `models.py` — JSON 배열 컬럼과 자기참조 외래키 버튼 모델. `button_views.py` — 부모 ID 로 트리를 내려가고 올라가는 뷰.

## 3. 이중 ORM  →  `3-dual-orm/`
**어디서** AI 상담 챗봇 서비스 (Django + FastAPI 계열) · 2025.06
**문제** Django 의 동기 처리 방식으로는 답변을 조각 단위로 흘려보낼 수 없었다. 관리자 화면은 이미 Django 로 만들어져 있어 전부 갈아엎을 시간은 없었다.
**바꾼 것** 관리자 화면(카테고리 CRUD · 로그 조회)은 Django 에 두고, 대화 응답 생성과 로그 추가만 FastAPI 로 떼어냈다. 두 프레임워크가 같은 MySQL 테이블을 다루게 되면서 FastAPI 쪽은 테이블 이름을 받아 런타임에 SQLAlchemy 모델을 만들고 캐시하는 방식을 썼다. 관계 삭제 정책도 이때 처음 CASCADE 와 SET NULL 을 구분해 선언했다.
**결과** 스트리밍은 가능해졌지만 같은 컬럼을 두 ORM 이 다르게 선언하는 일이 생겼다(불리언과 문자열, 길이 255 와 3000, 삭제 정책 CASCADE 와 SET NULL). 한쪽에만 정의된 테이블은 마이그레이션 이력에서 빠졌다. 이 경험이 다음 단계에서 스택을 하나로 합치는 근거가 됐다.
**코드** `django_models.py` — 관리자 쪽 테이블 정의. `fastapi_models.py` — 같은 테이블을 런타임에 다시 정의하는 모델 팩토리와 사용 예. `database.py` — 호스트명으로 분기하는 동기 엔진.

## 4. 계층 분리  →  `4-layered/`
**어디서** AI 글쓰기 검토 서비스 · 2025.08
**문제** React 와 FastAPI 만으로 새로 시작하면서 요청 검증, 비즈니스 규칙, DB 접근이 한 함수에 섞이는 것을 막아야 했다. 도메인 규칙(예: 콘텐츠가 쓰고 있는 카테고리는 지울 수 없다)이 쿼리 사이에 묻히면 다시 찾기 어려웠다.
**바꾼 것** 라우터(HTTP 만) · 서비스(규칙) · 저장소(DB 쿼리만) 세 층으로 나누고, 관리자 · 사용자 · 공통 세 영역으로 폴더를 갈랐다. 저장소 패턴 — DB 접근 코드를 한 곳에 모아 서비스가 SQL 을 모르게 하는 방식 — 을 따랐고, 함수 이름 규칙(조회 · 생성 · 수정 · 삭제 접두사)을 파일 머리에 적어 두었다. 테이블 이름은 공통 접두사로 통일하고 모든 관계에 외래키를 걸었으며 Alembic 으로 마이그레이션 이력을 남기기 시작했다.
**결과** 규칙이 어디 있는지 찾기 쉬워졌다. 다만 라우터가 매 함수마다 DB 세션과 인증을 프레임워크의 의존성 주입 문법으로 받아야 했고, 도메인이 서른 개 가까이 되자 라우터 · 서비스 · 저장소 폴더가 각각 부풀어 한 도메인을 고칠 때 세 폴더를 오가야 했다.
**코드** `type_router.py` — HTTP 만 받아 서비스로 넘기는 라우터. `type_service.py` — 삭제 가능 여부 같은 규칙을 판단하는 서비스. `type_repository.py` — 조인 · 페이징 쿼리만 담당하는 저장소.

## 5. 도메인 모듈  →  `5-domain-module/`
**어디서** 풀스택 베이스 템플릿 (현재 표준) · 2026.04~ (원형은 AI 캐릭터 대화 서비스 2025.11, 삭제 정책 예시는 복지관 ERP 2026.08)
**문제** 도메인 하나를 추가할 때 세 폴더에 파일을 만들고 각 라우터에 세션 · 인증 주입을 반복해야 했다. 설정 · 예외 · 응답 형식처럼 모든 도메인이 공유하는 코드와 도메인 고유 코드가 같은 층에 섞여 있었다.
**바꾼 것** 도메인마다 모델 · 저장소 · 서비스 · 라우터 4파일을 한 폴더에 두고, 설정 · DB 세션 · 예외 · 미들웨어 · 응답 형식은 코어로 뺐다. 요청마다 서비스 프로바이더 객체를 만들어 저장소와 서비스를 지연 생성하고(처음 쓸 때 만든다), 라우터는 데코레이터 두 개로 프로바이더 주입과 로그인 확인을 끝낸다. 외부 API 래퍼는 외부 연동 폴더 아래 서비스 파일만 두고 같은 프로바이더에 등록한다. 삭제 정책은 관계 성격에 따라 셋으로 나눴다 — 부속(첨부 파일)은 CASCADE, 기록이 달린 것(상담 대상자 · 계정과목)은 RESTRICT, 단순 참조(재원)는 SET NULL.
**결과** 새 도메인 추가는 폴더 하나와 등록 두 줄로 끝난다. 이 구조를 템플릿으로 굳혀 이후 프로젝트(복지관 ERP 15도메인, 전시관 AI 안내 19도메인, 팬 플랫폼 19도메인)가 같은 틀에서 시작했다.
**코드** `provider.py` — 지연 생성 서비스 프로바이더와 주입 · 로그인 데코레이터. `user_module.py` — 도메인 4파일 세트 한 벌. `delete_policy.py` — CASCADE · RESTRICT · SET NULL 을 관계 성격별로 나눈 모델.

## 지금 기준
베이스 템플릿의 백엔드는 FastAPI + SQLAlchemy 2.0 비동기 세션(aiomysql) 위에 코어와 도메인 모듈로 나뉜다. 도메인은 모델 · 저장소 · 서비스 · 라우터 4파일이 한 폴더에 있고, 새 도메인은 모델 등록과 라우터 등록 두 줄만 추가한다. 라우터는 프로바이더 주입 데코레이터로 서비스 프로바이더를 받고 로그인 데코레이터로 로그인 종류를 확인하며, 응답은 성공 · 실패 헬퍼로 형식을 통일한다. 외부 연동은 외부 연동 폴더 아래 서비스 파일만 두고 프로바이더에 지연 프로퍼티로 등록한다. 관계 삭제 정책은 부속 CASCADE · 기록 RESTRICT · 참조 SET NULL 을 기본으로 삼는다.
