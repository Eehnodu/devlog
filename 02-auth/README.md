## 1. Django 세션 로그인  →  `1-django-session/`
**어디서** AI 상담 챗봇 서비스 (초기 Django 계열) · 2025.02~04
**문제** 로그인이 필요한 사람은 관리자뿐이었다. 상담 위젯은 고객사 홈페이지의 iframe 안에서 돌았는데, 브라우저가 다른 도메인의 iframe 에는 기본 설정의 세션 쿠키를 보내 주지 않아 대화 상태가 끊겼다.
**바꾼 것** 관리자 로그인은 Django 의 인증 프레임워크와 서버 세션을 그대로 썼다. 세션 쿠키를 SameSite=None + Secure 로 열어 iframe 안에서도 전송되게 했고, 임베드를 막는 클릭재킹 방지 미들웨어는 꺼 두었다. 운영 · 로컬 구분은 서버 호스트명 규칙으로 했다.
**결과** 며칠 안에 납품할 수 있었다. 대신 위젯 쪽에는 인증이 전혀 없었고, 세션이 서버 메모리와 DB 에 묶여 있어 프론트를 분리하면 그대로 쓸 수 없는 구조였다.
**코드** `settings.py` — SameSite=None 세션 쿠키와 호스트명 분기. `admin_views.py` — Django 인증 프레임워크로 하는 관리자 로그인.

## 2. 첫 JWT 와 기기별 리프레시  →  `2-jwt-device-refresh/`
**어디서** AI 아바타 모의 면접 서비스 · 2025.05
**문제** React 단일 페이지 앱과 FastAPI 로 넘어오면서 Django 세션을 쓸 수 없게 됐다. 일반 사용자가 구글 · 카카오로 로그인해야 했고, 가입 없이 체험만 하는 사람도 받아야 했다.
**바꾼 것** JWT 를 처음 도입했다. 액세스 토큰은 1시간, 리프레시 토큰은 6시간으로 두고 둘 다 httpOnly 쿠키로 내렸다. 리프레시 토큰은 브라우저 · 기기 정보와 함께 DB 에 한 행씩 저장해서 재발급 때 저장된 값과 비교하고, 로그아웃은 그 기기 행만 지운다. 구글 · 카카오 OAuth 는 라이브러리 없이 인가 코드 → 제공자 토큰 → 사용자 정보 순서로 직접 호출했다. 게스트는 UUID 계정을 만들어 같은 형식의 토큰을 준다. 프론트에는 401 을 받으면 재발급 후 원래 요청을 한 번 다시 보내는 로직이 이때 처음 생겼다.
**결과** 기기별 로그아웃과 재발급이 가능해졌다. 다만 토큰 안에 닉네임 · 이메일 · 프로필 이미지를 그대로 넣었고, 리프레시 쿠키 수명(7일)이 토큰 수명(6시간)과 달라 쿠키는 있는데 토큰은 만료된 상태가 생겼다.
**코드** `user_service.py` — 토큰 생성 · 검증 · 쿠키 설정 · 재발급 · 로그아웃. `refresh_token_store.py` — (사용자, 기기) 단위 리프레시 토큰 테이블과 CRUD. `auth_router.py` — 구글 OAuth 직접 호출, 게스트 로그인, 재발급 엔드포인트.

## 3. 토큰 최소화와 정보 쿠키 분리  →  `3-claims-split/`
**어디서** AI 글쓰기 검토 서비스 · 2025.07
**문제** 회사 · 부서 · 역할까지 화면이 알아야 하는 정보가 늘었다. 이걸 전부 토큰에 넣으면 토큰이 커지고, 정보가 바뀔 때마다 토큰을 다시 구워야 했다. 반대로 매 요청마다 API 로 물어보면 화면 첫 렌더가 느려졌다.
**바꾼 것** 토큰에는 사용자 ID 와 역할만 담았다. 회사 · 부서처럼 화면 표시용 정보는 자격증명이 아니므로 스크립트가 읽을 수 있는 별도 쿠키에 base64 로 실었다. 재발급 때는 DB 에서 사용자를 다시 읽어 토큰과 정보 쿠키를 함께 새로 굽는다. 비밀번호 로그인이 생겨 서버 키를 섞은 HMAC-SHA256 으로 해시했다. 401 재발급 로직은 이 프로젝트에서 공용 API 훅으로 정착해 이후 전 프로젝트가 썼다.
**결과** 토큰은 작아지고 화면은 쿠키만 읽어 바로 그릴 수 있었다. HMAC-SHA256 은 비밀번호 전용 해시가 아니라는 점이 남아 다음 단계에서 바뀐다.
**코드** `auth_service.py` — ID · 역할만 담은 토큰과 별도 정보 쿠키, HMAC 해시, 재발급.

## 4. Argon2 와 관리자 · 사용자 세션 분리  →  `4-argon2-dual-session/`
**어디서** AI 캐릭터 대화 서비스 · 2025.11
**문제** 한 브라우저에서 관리자 화면과 사용자 화면을 함께 열면 같은 이름의 쿠키가 서로를 덮어썼다. 음성 대화가 WebSocket 으로 바뀌면서 소켓 연결에도 같은 인증이 필요했다.
**바꾼 것** 비밀번호 해시를 Argon2 로 바꿨다(passlib). 세션은 두 겹으로 갈랐다 — 쿠키 이름에 관리자 · 사용자 접두사를 붙이고, 토큰 안에도 종류 클레임을 넣어 접두사만 바꿔 끼운 토큰은 거절한다. 토큰 발급 · 검증 · 삭제를 한 클래스로 모으고, HTTP 요청과 WebSocket 핸드셰이크가 같은 검증 함수를 쓰게 했다. 라우터에는 로그인 종류를 인자로 받는 데코레이터를 두었다.
**결과** 관리자와 사용자가 같은 브라우저에서 동시에 로그인할 수 있고, 소켓도 쿠키만으로 인증된다. 이 구조가 그대로 템플릿 표준이 됐다.
**코드** `auth_token.py` — 접두사 + 종류 클레임 두 겹, HTTP · WebSocket 공용 검증. `login_decorators.py` — Argon2 해시와 로그인 종류 데코레이터(HTTP · WebSocket).

## 5. 계정 등급, 2단계 인증, 헤더 폴백  →  `5-grade-2fa/`
**어디서** 복지관 ERP · 2026.08 (헤더 폴백은 팬 플랫폼 서비스 · 2026.05)
**문제** 복지관 ERP 는 개인정보를 다루므로 비밀번호 한 단계로는 부족했고, 직원 · 관리자 · 최고관리자가 볼 수 있는 기능이 달라야 했다. 팬 플랫폼은 네이티브 앱의 웹뷰에서 쿠키가 실리지 않는 경우가 있어 로그아웃이 반복됐다.
**바꾼 것** 등급은 로그인 때 DB 에서 읽어 토큰에 넣고, 관리자 전용 API 는 허용 등급을 나열하는 데코레이터로 막는다. 화면 진입은 등급과 무관하게 열고 기능만 등급으로 가른다. 2단계는 비밀번호가 맞아도 로그인 토큰을 주지 않고 5분짜리 표식만 응답 본문으로 준 뒤, 계정에 등록된 번호로 6자리 인증번호를 보내고(Redis 에 60초 TTL, 재발송 30초 쿨다운) 맞으면 그때 토큰을 굽는다. 인증번호는 맞든 틀리든 한 번 쓰면 지운다. 시스템 관리자만 문자 장애 대비로 2단계를 건너뛴다. 팬 플랫폼은 쿠키가 없으면 Authorization 헤더와 리프레시 전용 헤더에서 토큰을 찾고, WebSocket 은 쿼리 파라미터를 폴백으로 둔다. 리프레시 수명은 호출마다 지정하고 쿠키 수명을 토큰 수명과 같은 값에서 계산한다.
**결과** 등급별 기능 제한과 2단계 인증이 데코레이터와 엔드포인트 세 개로 끝난다. 앱 로그아웃 반복은 헤더 폴백과 수명 정렬로 사라졌다.
**코드** `role_decorator.py` — 등급을 검사하는 데코레이터. `phone_two_factor.py` — 표식 토큰, 인증번호 발송 · 확인, 세 엔드포인트. `refresh_header_fallback.py` — 쿠키 → 헤더 → 쿼리 순서의 토큰 폴백과 수명 정렬.

## 지금 기준
베이스 템플릿은 4단계 구조를 그대로 표준으로 쓴다(`6-current-standard/auth_token.py`). 토큰 발급 · 검증 · 삭제는 한 클래스에 있고, 관리자 · 사용자 세션은 쿠키 접두사와 토큰 안의 종류 클레임 두 겹으로 나뉜다. HTTP 와 WebSocket 은 같은 검증 함수를 쓰며, 라우터는 로그인 종류를 인자로 받는 데코레이터 하나로 인증한다. 비밀번호는 Argon2, 소셜 로그인은 구글 · 카카오 직접 호출, 쿠키 도메인은 사이트 URL 설정 하나에서 도출한다. 계정 등급 데코레이터와 헤더 폴백은 프로젝트 요구에 따라 이 클래스 위에 덧붙인다.
